# 接入指南

写给要把这个服务接进客户端或后端的人。默认你没有参与过训练，遇到的每个词
都在正文里解释过一次。

---

## 0. 接前必读的三件事

**一、这个服务只做听写。** 音频进，文字出，默认不出声。两个入口，走的是同
一条处理链：

| 入口 | 什么时候用 | 说话期间 |
| --- | --- | --- |
| `POST /v1/audio/transcriptions` | 录完再送 | 不出字 |
| `WS /v1/realtime` | 边录边送 | 每秒刷一次预览 |

同一段录音从两个入口进来，出来的转写和润色逐字相同。选哪个只看客户端想不想
让用户边说边看到字。

**二、润色只删字，不改字。** 解码被限制成「输出必须是转写的子序列」：模型
每一步只能保留或跳过转写里的下一个字，写不出任何新字。所以「嗯、那个、就是」
这类口语词删得掉，而识别器听错的字一个也纠不了：「客户那边」听成「客户拿边」
就留在那里，这类错占字错率的 47%。换来的是模型永远编不出用户没说过的话。

**三、润色的第二个模型必须配上。** 润色其实是两个模型在同一份转写上并行工作
（详见 §5）。只配 `MINDSURF_POLISH` 不配 `MINDSURF_POLISH_TAGGER`，服务照常
返回 200，但 230 段真人长口述上，嗯/呃 的清除率从 0.9902 掉到 0.7781、整段
重复从 0.8889 掉到 0.5881。配漏了唯一能看出来的地方是 `/health` 的组件表里
少了 `polish-tagger` 这一项。

## 1. 快速启动

```bash
docker compose up
curl http://localhost:8000/v1/models
python examples/minimal_client.py turn.wav   # 单声道 16 位 16 kHz
```

`turn.wav` 要是一段真录音。数字静音演示不了这条链：服务对着静音会回答
「没听见」，这是对的，但什么也看不出来。例子脚本会先检查声道、位宽、采样率，因为
24 kHz 的音频送进 16 kHz 的口子不会报错，只会转写得很差。

没配模型时每个端点返回 503，`detail` 里会说清缺的是什么。

想让客户端能点朗读，再开一个开关。它默认关着，因为朗读走的是微软的托管服务，
要念的文本会离开本机：

```bash
MINDSURF_TTS=edge docker compose up
```

### 镜像有两个，默认那个能跑听写

`Dockerfile` 里两个阶段：

| 目标 | 大小 | 能干什么 |
| --- | ---: | --- |
| `base` | 433 MB | 只有 API 面。能启动、答 `/health`、对每个缺的引擎带原因拒绝 |
| `dictation`（默认） | 2.5 GB 起 | 转写 + 润色，完整的产品 |

`docker build .` 和 `docker compose up` 拿到的都是 `dictation`。只要 API 面就
`docker build --target base .`。

torch 从哪个源装取决于跑它的机器，不是这个仓库能替你决定的，所以留成参数：

```bash
docker build --build-arg PIP_EXTRA_INDEX_URL=https://download.pytorch.org/whl/cpu .
```

缺 Python 包会在装配期就拒绝，并说清要装哪个 extra。

听写还需要一份 MiniMind-O 的代码检出（润色器是用它自己的模型类加载的，不是
抄了一份代码），把检出挂进容器，再让 `MINIMIND_O_ROOT` 指过去。

## 2. 端点一览

协议兼容 OpenAI 的形状，客户端能复用现成的 SDK 习惯。

| 端点 | 用途 |
| --- | --- |
| `POST /v1/audio/transcriptions` | 语音转文本 |
| `POST /v1/audio/speech` | 朗读一段文本，客户端点小喇叭才调 |
| `GET /v1/models` | 当前路径、组件身份、许可 |
| `GET /v1/token-spec` | 特殊 token 规格（机器可读） |
| `GET /v1/licence` | 完整许可链 |
| `WS /v1/realtime` | 边录边送：说话期间出预览，松手给转写和润色 |
| `GET /health` | 就绪度，逐部件；降级返回 200，全不可用才 503 |

## 3. 音频格式是固定的

| 方向 | 格式 |
| --- | --- |
| 上行 | PCM16 / 16 kHz / 单声道 |
| 下行 | PCM16 / 24 kHz / 单声道 |

上行这两个数别写死在客户端里：`WS /v1/realtime` 连上后的 `session.created`
事件里带 `input_sample_rate`，按它来。

## 4. WebSocket：边录边送

事件名沿用 OpenAI Realtime API 的子集。客户端要处理的全部事件如下：

```javascript
const ws = new WebSocket("ws://localhost:8000/v1/realtime");

// 连上先收 session.created，里面有采样率，按它走
ws.onmessage = (event) => {
  const message = JSON.parse(event.data);
  switch (message.type) {
    // 说话期间的预览，只增不改，直接往后拼
    case "conversation.item.input_audio_transcription.delta":
      appendPreview(message.delta); break;
    // 松手之后：识别器听到的原文
    case "conversation.item.input_audio_transcription.completed":
      showTranscript(message.transcript); break;
    // 松手之后：去掉口语词的文本，放进输入框的是这个
    case "response.text.delta":
      putInTextBox(message.delta); break;
    case "response.done":
      turnFinished(); break;
    case "error":
      console.error(message.error.message); break;
  }
};

// 边说边发
ws.send(JSON.stringify({ type: "input_audio_buffer.append", audio: base64Pcm }));
// 说完
ws.send(JSON.stringify({ type: "input_audio_buffer.commit" }));
// 这一轮不要了
ws.send(JSON.stringify({ type: "response.cancel" }));
```

### 说话期间的预览

预览的增量**只增不改**：服务不会重发或修订已经发过的字，客户端拿到就往后拼，
不用做「已经显示的字后来变了」那套修订逻辑。第一个字约 2.5 秒出现，之后每秒
一批。

预览怎么来的、选哪个识别器，由 `MINDSURF_ASR_MODEL` 决定：

| 值 | 怎么出字 | 首字 | 预览字错率 | 占卡（实时率） |
| --- | --- | ---: | ---: | ---: |
| `sensevoice`（默认） | 每隔一秒把已收到的音频整个重读一遍，只把两次读数一致的开头发出去 | 2.5 s | **0.1094** | **0.057** |
| `paraformer-streaming` | 流式模型边解码边写，从不回头 | **0.6 s** | 0.2796 | 0.323 |

默认那条便宜约六倍、准两倍半，代价是首字慢两秒。流式那条首字快，但一块听错
就错到松手。名字不在这两个里的，装配期就拒绝。选流式时可以用
`MINDSURF_ASR_STREAMING` 指向本地权重目录；不设的话 FunASR 会按名字去
ModelScope 下载，这一步要联网。

默认那条的刷新间隔是 `MINDSURF_PREVIEW_SECONDS`（默认 1.0 秒）。别设到 1.0
以下。0.5 秒间隔实测是坏的：两次相隔太近的读数会在还没定型的尾巴上达成一致，
「一致」就不再意味着「稳了」。设 0 完全关掉预览，松手前不出字。四段真听写上，
1 秒和 2 秒间隔下预览显示的文本都和松手后的最终转写逐字相同。

预览还有两个内部参数没有暴露成配置，值都扫过：开始读之前先攒 1.5 秒音频
（0.5、1.0、2.0 都试过，1.5 是唯一四段全对的），一次最多重读 45 秒（超过就在
静音处切一刀，把之前的定稿冻结，否则整段重读的开销随时长平方增长）。

一条要紧的限制：**预览只在「一个人对着麦克风口述」这个场景上稳。** 同一套
测试放到双人对话录音上，八段里零段和最终转写一致。抢话、重叠、改口会让
识别器反复改主意。另外验证用的四段录音都只有 13.5 到 13.9 秒，一分钟以上的
真听写录音仓库里没有。预览漂了不是正确性问题（最终文本由松手后那条路交付），
是屏幕闪烁的问题。

**无论选哪个识别器，预览都只驱动显示。** 松手之后走的是整段转写加润色，用户
最终留下的文字来自那里。

### 松手之后回什么

两个事件，装的东西不同：

```json
{"type": "conversation.item.input_audio_transcription.completed", "transcript": "嗯，那个会议改到下午三点了"}
{"type": "response.text.delta", "delta": "会议改到下午三点了"}
```

`completed` 是识别器听到的原文，`response.text.delta` 是去掉口语词之后的文本。
放进输入框的是后者。

润色环节抛异常时不会把转写一起吞掉：`response.text.delta` 里会退回原始转写。
口语词留着只是差一点的转写，转写丢了是丢了一次听写。

### 一次 commit 里说太久会怎样

服务会按模型训练时见过的长度把长转写拆开处理：实测 124 秒的口述转写出 553
字，不拆模型会返回空字符串，拆了正常。超过约 1300 字连拆都救不回来，这时返回
`error` 事件。所以客户端最好每说完一段就 commit，不要攒到最后。拆分完全发生
在服务端，客户端不用做任何事。

### 出错丢帧，不丢连接

发了服务不认识的事件会收到 `error` 帧，不会被静默忽略。帧解析失败（二进制帧、
非 JSON 文本、`audio` 字段不是合法 base64）丢的是那一帧，不是连接。以前这
四种都会直接 1006 断开且不给原因，客户端编码器出一次错，用户丢的是整段口述。

### 取消与换人

`response.cancel` 取消当前这一轮：正在跑的转写和润色都停掉，GPU 跟着停。

取消后缓冲区的处理分两种，别记反：已经 commit、正在转写时取消，**缓冲区保留**
——用户不想要这段文字，但音频还在，可以重来；还没 commit 就取消，**缓冲区清空**
——那是一段没说完的话，留着会漏进下一轮。取消之后不要假设缓冲区是空的，
`input_audio_buffer.clear` 是显式清空的那个事件。

一条连接可以连着口述很多轮，轮与轮互相独立，上一轮说了什么不影响下一轮的
转写。换人时发 `session.clear`，回执和连接建立时一样是 `session.created`。
`response.done` 里还带一个 `context` 计数字段，是早期设计留下的，听写用不上，
忽略即可。

## 5. 润色：配置与效果

润色是可选的一跳，`MINDSURF_POLISH` 指向一个 checkpoint 才开：

```bash
export MINDSURF_POLISH=/app/weights/sft_polish6_768.pth
```

开了之后响应多一个字段：

```json
{"text": "那个今天天气怎么样", "polished": "今天天气怎么样", "language": "zh"}
```

`polished` 是 `null` 表示这个服务没接润色，不是「这段不用润色」。两者要分开
处理，前端别写成 `polished || text`。路径不存在的话服务启动时就拒绝，不会等
到第一句话才炸。用的哪份权重，看 `GET /v1/models` 里 `polisher` 那一项的
`sha256`。

### 第二条臂

```bash
export MINDSURF_POLISH_TAGGER=/app/weights/polish_tagger_unionchar.pt
export MINDSURF_POLISH_TAGGER_BACKBONE=/app/weights/polish_tagger_unionchar_backbone.pth
export MINDSURF_POLISH_TAGGER_THRESHOLD=0.4   # 可省，默认就是 0.4
```

润色是两个模型并行工作：一个生成式模型（上面那个），一个逐字打分的标注器
（这三行）。两边的结果按「veto」合并：默认两边都说删才删，只有两类例外（
词表里的口语词、紧挨着的整段重复），一边认出来就删。生成式擅长口语词，标注器
擅长重复，强项互补。

这条臂是承重的，不是锦上添花：230 段真人长口述上，两条臂合起来删掉 0.9902 的
嗯/呃 和 0.8889 的整段重复，生成式单独跑是 0.7781 和 0.5881。不配它，四分之一
的口语词和三分之一的重复会留在用户的输入框里，而服务不报任何错。`/health` 和
`/v1/models` 的组件表里会出现 `polish-tagger`，带自己的 `sha256`，看那里确认
接没接上。

为什么是 veto 不是别的合并法，量过：换成 union（任一边说删就删），重复召回
涨 0.027，但误删从每千字 11.57 涨到 142.62，230 句里 34 句的否定词被删掉、
意思反了。

配置上的两条硬规矩：`MINDSURF_POLISH_TAGGER` 和它的 `BACKBONE` 必须成对，
只设一个装配期就拒（标注头是从那份骨干上调出来的，单给一半没有意义）；只设
标注器不设 `MINDSURF_POLISH` 也拒，它是第二条臂，没有第一条臂可合。

### 当前效果

986 条留出集（训练时藏起来专门考试用的句子），RTX 4090，服务真路径，标注器
阈值 0.4。表里的「自拟线」是算法侧自己定的工作标尺，不是小组 OKR 的验收线。

| | 不润色 | 只有生成式 | **现在的产品** | 只能删的最好结果 | 自拟线 |
| --- | ---: | ---: | ---: | ---: | --- |
| 与原文的字错率 | 0.1060 | 0.0435 | **0.0269** | 0.0156 | ≤ 0.02 |
| 口语词清除 | 0 | 0.8643 | **0.9722** | 0.9966 | ≥ 0.90 |
| 内容保留 | 0.9868 | 0.9726 | **0.9803** | 0.9866 | ≥ 0.98 |
| 编造 | 0.1054 | 0.0287 | **0.0199** | 0.0150 | ≤ 0.02 |
| 空输出 | 0 | 0 | **0** | 0 | 0 |
| 切穿词 | — | — | **0/986** | — | — |

「过没过线」按重抽比例读，不按单个点：把 986 条反复重抽 4000 次，每次重算，
看指标有多少次仍落在线内侧。

| | 值 | 线 | 重抽里落在线内侧 |
| --- | ---: | --- | --- |
| 口语词清除 | 0.9722 | ≥ 0.90 | 100% |
| 空输出 | 0 | 0 | — |
| 内容保留 | 0.9803 | ≥ 0.98 | 62% |
| 编造 | 0.0199 | ≤ 0.02 | 54% |
| 与原文的字错率 | 0.0269 | ≤ 0.02 | 0% |

清除和空输出是稳的。内容保留和编造贴在线上，重抽里只有六成和五成落在内侧，
正确的说法是「和线分不清」，不是「过了」。字错率明确没过。

字错率没过，构成要读清楚：0.0269 里 0.0127 是识别器听错的字，只能删的约束下
润色器改不了；0.0041 是把语料自带的口语词也删了，对听写产品那是对的。两项相加
0.0168 是这套架构在这把尺子上的地板，地板在 0.02 以下。所以线不是不可达，
可达的还剩约 0.010。拆解在 `artifacts/polish-cer-split-2026-08-16.json`。

「切穿词」问的是「存不存在一种对齐方式是不切词的」，不是「difflib 恰好选的
那种切不切」。重复串里同一个删除有多种等价的对齐，只按一种判会把正常输出
（「先熟悉」「太平洋」）误报成缺陷。

### 延迟

整轮（13.8 秒口述，一路在飞）：P50 198 ms、P95 204 ms。其中润色那一跳中位
120.6 ms、P95 473.9 ms。RTX 4090，服务真路径。

同一条链在 RTX 5070 笔记本上是中位 300 ms、P95 1197 ms。两台机器差 1.5 到
5 倍，别把一台的数当另一台用。

## 6. 一张卡能同时扛几路

RTX 4090，13.8 秒真实口述，每档 24 个请求，转写加润色都算在内：

| 在飞 | 吞吐 | P50 | P95 | 失败 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 5.04/s | 198 ms | 204 ms | 0/24 |
| 2 | 5.72 | 348 | 374 | 0/24 |
| 4 | 8.08 | 492 | 546 | 0/24 |
| **8** | **9.83** | 797 | **860** | 0/24 |
| 12 | 9.85 | 1077 | 1940 | 0/24 |
| 16 | **10.14 ← 峰** | 1553 | 2201 | 0/24 |
| 24 | 9.73 | 2301 | 2462 | 0/24 |

1 到 24 全程零失败。**建议把在飞上限设成 8**：吞吐已是峰值的 97%，再往上一档
P95 就翻倍。8 恰好等于服务内部的批大小 `max_batch=8` 不是巧合：超过批大小的
并发只是在排队。

三条限定，读表前要知道：这张表量的是整轮（收音频、转写、润色都在内），拿它和
纯语言模型的生成吞吐并排比是比错了东西；这台 4090 上还常驻着一个后端容器
（约 4 GB）；单条音频 13.8 秒，口述更长时攒批的收益会变。

单独量润色这一级，在飞 32：14.23 请求/秒、P50 2622 ms、含 prompt 3678
token/秒。

### 如果哪天并发真的上来了：vLLM 的数

同一份权重导成 `Qwen3ForCausalLM` 挂上 vLLM（导出后拿同一个 prompt 对 logits，
最大绝对差 0），在飞 32 跑出 96.55 请求/秒、P50 384 ms。要紧的不是倍数是形状：
我们的 P50 随并发线性变差（472 → 2622 ms），vLLM 几乎是平的（368 → 384 ms），
因为我们的批处理里一个请求要等整批里最慢的那个，continuous batching 没有这个
问题。

只能删的解码约束能带过去（`AdapterLogitsProcessor` + `extra_args`，要声明
`is_argmax_invariant()=False`）：带约束 154.21 请求/秒，是自由生成的 56%，
256 条输出全部仍是转写的子序列，零例外。折算是我们进程内实现的 10.3 倍，在
`vllm/vllm-openai:v0.26.0` 镜像里独立复现过一次。搬不搬是部署的决定，
`scripts/vllm_copy_constraint.py` 是能直接跑的实现。

照着做的人会踩的两个坑：v0.26 的 `vllm serve` 去掉了 `--disable-log-requests`，
`--model` 退成位置参数；更要紧的是必须走 `/v1/chat/completions` 让 vLLM 套上
chat template。拿 `/v1/completions` 发裸 prompt，模型 64 次全回空串，而吞吐
读出 653 请求/秒，那是它生成零个字的速度。

### 加了并发闸之后

识别器后来限制成一次只跑一个前向。这和直觉相反地让吞吐更高、尾延迟更低：
两个前向在一张卡上本来就不重叠，驱动会串行化内核，并发只是互相打乱显存和
调度。同一台 4090，22.2 秒口述，新老代码交替发：

| 在飞 | 老吞吐 | 新吞吐 | 老 P95 | 新 P95 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 2.05/s | 1.83/s | 544 ms | 570 ms |
| 2 | 2.06 | **2.90** | 1065 | **702** |
| 4 | 4.57 | 4.74 | 931 | 901 |
| 8 | 6.29 | **7.14** | 1347 | **1183** |
| 16 | 7.25 | **8.62** | 2933 | **2407** |

这一轮量的时候卡上有别的进程，绝对值偏高；两个服务交替发，所以横向比较成立，
绝对值以上面那张独占卡的表为准。

## 7. 长录音：整段发过来会静默丢内容

这是修掉的问题里最重的一条。之前只在 600 秒和 1100 秒上量过延迟和显存，没量
过它写对没有。量了之后发现：整段音频走一次前向，字错率随长度爆炸，而且没有
任何报错，HTTP 200。

| 口述长度 | 整段一次前向 | 按停顿分段 | 逐句单独转写（上界） |
| ---: | ---: | ---: | ---: |
| 22 秒 | 0.0128 | 0.0128 | 0.0128 |
| 81 秒 | 0.0198 | 0.0198 | 0.0165 |
| 110 秒 | 0.0189 | **0.0165** | 0.0118 |
| 315 秒 | 0.0194 | **0.0113** | 0.0105 |
| 900 秒 | **0.1373** | **0.0125** | 0.0105 |

900 秒那条最难看：说了 4243 个字，整段转写出来 3409 个，丢了 834 个，列表
编号和句号全塌成一行流水：

```
整段：…比如故宫添坛一和源等…一准备材料面条肉末从姜蒜辣椒油盐酱油料酒等2将面条放入废水中煮熟
分段：…比如故宫、天坛、颐和园等。…一、准备材料、面条、肉末、葱姜蒜、辣椒油、盐、酱油、料酒等。2、将面条放入沸水中煮熟，
```

现在的行为：90 秒以上按停顿切开逐段转写，90 秒以下不切（那以下切不切逐字
相同，切开只多花一次前向）。三个常量在 `src/mindsurf_omni/service/vad.py`：
目标段长 25 秒、硬上限 45 秒、停顿判定 200 毫秒。

代价和收益：

| 口述长度 | 整段耗时 | 分段耗时 | 只处理最后一段 |
| ---: | ---: | ---: | ---: |
| 110 秒 | 145 ms | 278 ms | 49 ms |
| 315 秒 | 648 ms | 692 ms | 53 ms |
| 900 秒 | 4263 ms | **1861 ms** | 54 ms |

90 到 300 秒这一档多花 100 到 130 毫秒；300 秒以上分段反而更快，因为注意力的
开销是平方的。

最右那一列是给客户端看的：如果客户端边录边送（`WS /v1/realtime`），前面的段
在说话期间就转完了，松手后的等待就是这一列，不管录了多长都是五十几毫秒。
HTTP 端点是整段收完再算，拿到的是中间那列。

分段之后单次前向有了大小上界，1200 秒录音问显存分配器要 44 GiB 的那条路
没有了，所以入口上限从 1000 秒放宽到 3600 秒。剩下的约束是请求体大小（一小时
16 kHz PCM16 是 115 MB），不是显存。

这些数是在合成语音上量的（160 条 TTS 音频拼接），停顿分布是合成器的不是人的。
仓库里没有真人长录音，90 秒这个拐点在真人身上可能会动。

## 8. 热词：把说话人自己的专名放回去

识别器不认识的专名（人名、产品名、楼号）可以用 `MINDSURF_HOTWORDS` 配一张表，
逗号分隔：

```bash
export MINDSURF_HOTWORDS=吕鑫,通义千问,明德楼
```

原理是按无声调拼音在转写上做整词替换。SenseVoice 没有热词输入口（它的
`generate` 只收音频和语种），所以这是转写之后的一遍后处理，不是解码期的偏置。

**这个功能的风险全在反方向，所以主判据是「没碰的有多少」，不是「修好了几条」。**
「部署」和「不熟」同音，「李工」和「理工」同音，表里放进任何一个，另一个所在
的每个普通句子都会被改成胡话。两道闸挡着：

- **装配时**拒绝同音撞上常用词的条目（jieba 词频 ≥ 10）。这一条拒掉「不熟」
  （撞「部署」，频次 3333）、「断连」（撞「锻炼」，1689）、「李工」（撞
  「理工」，490）。拒绝而不是静默跳过：一张一半条目失效的表，操作员配了、
  服务报了就绪、词一次也没出现，没有任何地方说得出是哪一半失效。
- **请求时**放过分词器已经读成普通文本的跨度。「先统一前文的术语」里的
  「统一前文」是两个日常词，凑巧和「通义千问」同音；「今天履新」里的「履新」
  是词典词。这两个都不碰。

效果：

| | |
| --- | --- |
| 2855 条真语料（986 留出集 ×2、723 条 CS2W 真人转写、160 条固定文本），两张表 | **改动 0 条** |
| 端到端 19 句（合成语音 → 真识别器 → 这一级）：识别器听错 | 6 句 |
| 其中修回 | **3 句** |
| 10 句陷阱里改坏 | 1 句 |
| 每条转写的额外耗时 | 0.38 ms |

改坏的那一句是这套做法的天花板，不是能修的缺陷：

```
想说 新来的同事今天履新。
听成 新来的同事，今天旅欣。   ← 识别器先错了，旅欣 不是词
改成 新来的同事，今天吕鑫。
```

同音表读的是声音。说话人说了个和热词同音、又被识别器写坏的词，没有任何信息
能分开这两种情况。识别器听对的那份（「他刚刚履新上任」）这一级不碰。

**够不着的两类。** 一类是声母不同的：「李欣」对「吕鑫」，无声调拼音也不同音，
表匹配不上。试过放宽到前后鼻音，反而更差：「吕鑫」折叠后撞上「履行」（1684）
被装配闸拒掉，修回从 3/6 掉到 2/6。另一类是被分词器读成几个正常词的：句首的
「通一千问」切成「通/一千/问」，三块都是词典词，这一级当它是普通文本。试过
要求「每一块都得是多字词」好把它捞回来，结果把放行面从 5.6% 的跨度开到
23.0%，中文单字词遍地都是。一条召回换四倍的暴露面，退回去了。

这一级也守着一条类似只能删的约束：输出里的字要么本来就在转写里，要么在热词
表里，替换是等字数的整词，不加字不减字。

### 为什么不换成解码期偏置

业界主流（Deepgram Nova-3 的 `keyterm`）把热词做进模型，中文开源对应的是
FunASR 的 SeACo-Paraformer。它是唯一能治「声母不同」那类的路子。同一批 19 句
探针上比过：

| | 热词命中 | 陷阱改坏 | 中位耗时 | 标点 / ITN |
| --- | ---: | ---: | ---: | --- |
| SenseVoice 裸的 | 4/9 | — | 50 ms | 有 |
| **SenseVoice + 我们的后处理** | 8/9 | **1/10** | **50 ms** | 有 |
| SeACo-Paraformer 裸的 | 4/9 | — | 208 ms | 无 |
| SeACo-Paraformer + 解码期热词 | **9/9** | 3/10 | 213 ms | 无 |

它确实修回了我们够不着的那条（「李欣明天来开会」→「吕鑫明天来开会」）。
不换的三个理由：误伤翻三倍，而且偏置发生在解码里，事后没有地方撤；慢四倍；
它不写标点、不做数字转换，接上去还要再挂一个标点模型，而那个模型上一轮已经
量过会让正常听写变差。按「每修回一条赔几条」算，我们 1 赔 4，它 3 赔 5。

## 9. 多语言

识别器支持 zh / en / yue / ja / ko。润色这一级分三种待遇。「不支持」和
「弄坏」是两件事，要分开说：

| 语种 | 润色 | 怎么做的 |
| --- | --- | --- |
| 中文 | 模型 | 生成式 + 逐字标注器，veto 合并 |
| 英文 | **规则** | 填充音 `um/uh/er/erm/uhh` + 相邻重复删一份。模型在这一格没有发言权 |
| 粤 / 日 / 韩 | 原样通过 | 不进模型，一个字不动 |

### 英文为什么走规则

中文训出来的润色器在英文上会留下每一个填充音、却删掉实词。拿 Disfl-QA
（`google-research-datasets/Disfl-QA`，CC BY 4.0）的干净句子注入填充音与重复，
300 句：

| 臂 | 完全一致 | 该删没删（词） | 不该删删了（词） |
| --- | ---: | ---: | ---: |
| 只有模型 | 38/300 | 584 | 0 |
| **只有规则** | **265/300** | 35 | **0** |

所以纯拉丁片段模型没有发言权。规则只做两件无歧义的事。话语标记（`like` /
`well` / `actually` / `right` / `you know` / `I mean`）一个都不碰：它们是英文
版的两栖词，`I like the layout` 和 `it's, like, twice as fast` 是同样四个
字母，能划这条线的人工标注语料我们没有。英文的合法叠词也保护着：`Pago Pago`
（地名）、`had had`（过去完成时）、`very very`（强调）。句中大写词当专名，
`I` 除外：它永远大写，大写在它身上不带信息，而 `I I` 是最常见的口吃。

### 明确不做的一类

改口型不流利：`Who did no What did the government want…`。它要识别被改掉的
那半句，是理解不是删除。Disfl-QA 原样 300 句，模型 0/300、规则 1/300——谁都
做不了，写在这里免得下一个人以为是漏做。

### 粤日韩

`worth_polishing` 对它们恒假，这一级不动它们。44 条多语言探针里日 3/3、
韩 2/2、粤 2/2 原样通过。

### 短音频的语言判定

短于 1.5 秒的音频语言判不准（半秒的「嗯」会被判成日语），所以短音频直接用
部署声明的语言（`MINDSURF_ASR_LANGUAGE`，默认 `zh`），长音频照旧自动判。

## 10. 请求上几乎没有可调的参数，这是故意的

听写是确定性的：同一段音频进来，出去的永远是同一段文字。转写和润色都是贪心
解码，没有温度、没有采样，请求里也不收这些参数。这不是没做完，是听写产品
该有的样子——用户重录一遍，不应该得到另一个版本的文字。

唯一被显式拒绝的参数是朗读接口的 `speed`（400）。语速该在播放端调：

- 网页或 webview 用 `audio.playbackRate`，默认保音高，对已取回的音频直接
  生效，不用重发请求。1x 到 1.75x 是可用区间，超过 2x 音质明显劣化。
- 服务端做的话要重新合成一遍，离线时调不了。

什么时候来找我们：音频不在 webview 里播（原生播放器），或者要导出文件发给
别人听。那两种情况 `playbackRate` 够不着，说一声我们在 edge 上接。

## 11. 出错时

| 状态 | 含义 | 该做什么 |
| --- | --- | --- |
| 503 | 没配引擎，或那一段还没接上 | 看 detail，它会点名缺的是哪个**变量**（不给路径，那是服务器上的东西） |
| 400 | 请求体没有音频；或 wav 不是 16 bit 单声道 | 看 detail 分辨这两种。第二种要转成 16 bit 单声道，不是「有没有发 PCM」的问题 |
| 413 | 录音比这个端点一次收的长 | detail 里带实际秒数和上限，按它分段发 |
| 415 | body 裹在这条路不拆的壳里（multipart、gzip 等） | 直接发裸 PCM 或整个 wav，别用 `files=`，别压缩 |
| 500 | 兜底，正文是 JSON，带 `X-Request-Id` | 拿这个 id 去对服务端日志 |
| WS `error` 帧 | 事件类型不认识，或缓冲区为空 | 看 `error.message` |

错误信息会写清楚是什么坏了、怎么修。碰到看不懂的错误信息报给我谢谢喵。

## 12. 换 checkpoint 不用改配置

加载器从权重文件里读形状、校参数量，对不上就拒绝加载。所以把路径指错到一个
形状不同的文件，几乎都会在启动时炸出来，而不是安静地变差。唯一安静的错法是
指到另一份形状相同的旧权重——防这个靠 `GET /v1/models` 里每个组件的 `sha256`，
和你部署时算的文件哈希对一下。细节见[训练说明 §1](TRAINING.md#1-模型)。

## 第三部分：问题排查

## 13. 服务起不来

### 每个端点都返回 503：这是正常状态

没配引擎时服务照样启动，每个端点都答 503 并说明缺什么。设上引擎就好：

```bash
MINDSURF_ENGINE=cascade docker compose up
```

### 启动直接退出

```text
the cascade path needs these, and the file each names is not on disk:
MINDSURF_TOKENIZER, MINDSURF_ASR
-- mount the weights directory or set the matching variable
```

按名字挂载或设对应变量。报文里只有变量名，没有路径——这些端点不需要认证，
而绝对路径会暴露服务器上的用户名和目录结构。路径写在服务端日志里。

### 起来了，但删得明显少

九成是标注器没配上（只设了 `MINDSURF_POLISH`）。看 `/health` 的组件表里有
没有 `polish-tagger`，没有就补上 §5 那三行。

### 起来了，但怀疑权重指错了

```bash
curl -s localhost:8000/v1/models | python -m json.tool | grep -A2 polisher
```

`polisher` 的 `sha256` 和你手里文件的哈希对不上就是指错了。指错形状相同的
旧权重不会报任何错，服务一样应答，只是效果差。

### `/health` 报 `degraded`

看 `not_ready` 那一栏，它列的是哪一段缺配置。组件本身没坏不代表整条链走
得通。

## 14. 延迟问题

### 松手后文字来得太晚

先分账再优化，单一总时长只告诉你慢了：

```bash
python scripts/smoke_service.py --base http://localhost:8000   # 打印首个增量耗时
```

大头通常不是模型慢，是「什么时候开始出字」。松手后那条路要整轮跑完才出第一
个字；说话期间的预览是另一条路，每秒重读一次已收到的音频。想让用户早看到字，
接 WebSocket 的预览。

### 首字忽然涨到秒级，而且越用越慢

先看空闲时的 GPU 占用：

```bash
nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader   # 空闲时必须是 0 %
```

不是 0，说明有生成还在给已经断开的调用方跑，占着卡。这个问题已修（客户端
断开时服务端每步检查停止位），有回归测试盯着；再出现就是回归。

### WebSocket 一直没有回复

先确认发的事件类型服务认识——不认识的事件会收到 `error` 帧，不会静默。一个
帧都收不到是连接问题。取消与缓冲区的语义见 §4 末尾，别假设取消之后缓冲区
是空的。

## 15. 评测问题

### 指标标着「仅报告」

意思是这个指标这次不参与通过与否的判定，只印出来参考。原因是它分辨不了我们
关心的那点差别：比如单看一边的错字率，这批数据能分辨的最小差别是 0.0529，
而我们关心的差别是 0.0500，比分辨力还小，它给出什么结论都不作数。要让它作数
得加样本量或换测法，不是把阈值放宽。

### 错字率高得离谱

先确认用来听的是第三方识别器，不是我们自己的部件。拿模型自己的部件给模型
打分是循环论证，`require_independent_judge` 会拒绝服务组件，也会拒绝和被测
对象同源的识别器。

### 对比结果写着「无法区分」

意思是两边的差别落在这批数据的测量误差里，数据不支持说谁好谁坏。想下结论
就得加样本量——虽然加了也可能还是落在噪声里。
