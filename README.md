# MindSurf Omni

按住快捷键说话，松开，一段干净的文字出现在输入框里。这个仓库是这件事的算法侧，
训练组的交付仓库。

整条链只做三件事：把语音转成文字（SenseVoice-Small，上游模型，我们没动它）；
把转写里的「嗯、那个、就是」这类口语词删掉（我们自己训练的润色器，这个仓库的
主体就是它）；用户点小喇叭的时候把文字念出来（edge-tts，默认关着）。
不点就不出声。

读数在 [§3](#3-指标)，怎么接在[接入指南](docs/INTEGRATION.md)，
润色器怎么训的在[训练说明](docs/TRAINING.md)。

## 定位

- 识别器 SenseVoice-Small 234M，润色器 139M，合计 373M。
  笔记本上跑得动，不联网，录音不出本机。
- 4090 上一段 13.8 秒的口述，从松开到文字出来 198 毫秒，用户感觉不到等待。
- 防编造靠规则不靠运气。解码时模型只被允许做一件事：把转写里的字保留或删掉。
  它没有任何机会写出转写里没有的字，所以「嗯、那个」删得掉，
  而用户没说过的话它结构上就编不出来。

### 跟同一量级的对手比

对手选 Whisper small（240.6M，MacWhisper、superwhisper、whisper.cpp 的默认
选择）。同一批音频、同一台 4090，字错率都按数字折叠的口径算：「301」和
「三零一」算同一个答案，不然识别器开着 ITN 时每个数字都会被记成好几处替换。

先交代一个不齐的地方：测速脚本给 Whisper 显式传了 `fp16=True`，SenseVoice 走
FunASR 默认的 fp32。所以显存那一列对 SenseVoice 偏高，延迟那一列对 Whisper
偏优。

| | 参数 | 字错率 | P50 | 峰值显存 |
| --- | ---: | ---: | ---: | ---: |
| 真人自发口述 60 段 | | | | |
| Whisper small | 240.6M | 0.3045 | 398 ms | 1403 MB |
| **SenseVoice-Small** | 234.0M | **0.1830** | **55 ms** | **1044 MB** |

早先我们还报过一行 AISHELL-1 上的 0.0614，后来发现那个数是自己造出来的，
撤了。错在取样：400 条是从排好序的目录里取前 400，而 AISHELL 的 test 集按
说话人分目录、每人约 370 条，我们取到的其实是一个说话人零一点。改成全部
7176 条、20 个说话人、繁转简、去标点之后，读数 0.0295，和上游自报的 0.0296
逐位对上。Whisper 那行的 0.1333 是用同一套错口径量的，要重新并表得把它也
重量一遍，还没做，所以这一行先不给。

这两张表说的是中文口述这一个场景。Whisper 是多语种通才，在中文上本来吃亏；
英文侧我们没有带参照的语料，没量。不能引申成「全方位更好」。

Whisper 只转写，不清口语词。清口语词的产品（Wispr Flow、Gboard 的 Rambler）
都在云上跑大模型。本地、小、带润色，三样同时成立的，我们没找到第二个。

语言：识别支持 zh / en / yue / ja / ko。润色中文靠模型、英文靠规则、
其余语种原样通过。「不支持」和「弄坏」在我们的判据里是分开记的两件事，
细账在 [`headline_numbers.json`](configs/release/headline_numbers.json) 的
`dictation_multilingual`。

## 1. 链路

```text
麦克风 ─► SenseVoice 转写 ─► 润色（删口语词）─► 文本框
                                  │
                                  └─► 点小喇叭才走：edge-tts 念一遍
```

润色这一级是两个互相独立的模型在同一份转写上各删各的，然后合并：
一个生成式模型（被锁成只能删字），一个逐字打分的标注器。合并规则是两边都
说删才删，只有两类例外（词表里的口语词、紧挨着的整段重复），这两类一边认出来
就删。生成式擅长口语词，标注器擅长重复，强项刚好不重合。

这两条缺一条差很多。230 段真人长口述上，两条一起能删掉 99% 的 嗯/呃 和
89% 的整段重复；只有生成式那条单独跑，掉到 78% 和 59%。部署时想确认标注器
接没接，看 `/health` 的组件表里有没有 `polish-tagger`，那是唯一看得出来的
地方：配漏了服务照样正常应答，只是删得少。

朗读是用户主动点的，一整轮听写里没有任何环节会自动念出声。音色是拿六个候选
把同一条笔记各念一遍、用耳朵选的（晓晓）：被淘汰的两个把「下载」的「载」念成
第四声，这种错任何字级判据都看不见，只能听。

两个入口，同一条链，出来的文字逐字相同，选哪个只看客户端想不想边说边显示：

| 入口 | 什么时候用 | 说话期间 |
| --- | --- | --- |
| `POST /v1/audio/transcriptions` | 录完再送 | 不出字 |
| `WS /v1/realtime` | 边录边送 | 每秒刷一次预览 |

## 2. 交付物

听写要三份权重：

| 文件 | 干什么 |
| --- | --- |
| `sft_polish6_768.pth` | 生成式那条臂，被约束成只能删 |
| `polish_tagger_unionchar.pt` | 逐字标注器，第二条臂 |
| `polish_tagger_unionchar_backbone.pth` | 标注器的骨干 |

识别用上游的 SenseVoice-Small，朗读用 edge-tts，两个都没改过。

| | 地址 |
| --- | --- |
| 代码、文档、逐条证据 | 这个仓库 |
| 权重、tokenizer、配置 | [`oscar0403/mindsurf-omni`](https://huggingface.co/oscar0403/mindsurf-omni) |

有三样东西不在交付里，各有各的理由：

**客户端。** 事件发出去了、格式冻结了、文档写了。怎么渲染增量、松手时怎么把
文字放进输入框，是前端的活。

**vLLM。** 同一份权重挂上 vLLM、带着复制约束，能跑到我们进程内实现的 10.3 倍
（37768 对 3678 含 prompt tok/s，256 条输出无一例外仍是转写的子序列）。但换
推理后端是部署的决定，不是内核的一部分：`grep -ri vllm src/` 是 0 行，以后也
应该是。我们交的是论据和一份能直接跑的实现
（`scripts/vllm_copy_constraint.py`）。按现在的量级其实用不上：进程内整轮
10.14 轮/秒，一轮约 14 秒语音，一张 4090 够约 140 个人同时不停地口述。vLLM
真正改变的是高并发下的延迟形状：我们的 P50 随并发线性变差（472 → 2622 ms），
它几乎是平的（368 → 384 ms）。并发真上来了再考虑。

**先前那条会说话的助手线。** 上游的 Talker 接我们自己的 Thinker，两次 DPO 再
把权重差加起来，成品 `sft_merge_768.pth`。它验证过，按数据选择不投产。产品
转成听写之后仓库按听写收口，那条线的源码和量具不再上传。文件在本地，git
历史里也完整保留着 2026-08-28 之前的每一版。

## 3. 指标

986 条留出集（训练时藏起来专门用来考试的句子），RTX 4090 上走服务真路径。
下面的「线」是算法侧自拟的工作标尺，不是小组 OKR 的验收线。

| | 值 | 不润色时 | 自拟线 | 重抽里落在线内侧 |
| --- | ---: | ---: | --- | --- |
| 口语词清除 | **0.9722** | 0 | ≥ 0.90 | 100% |
| 空输出 | **0** | 0 | 0 | — |
| 内容保留 | **0.9803** | 0.9868 | ≥ 0.98 | 62% |
| 编造 | **0.0199** | 0.1054 | ≤ 0.02 | 54% |
| 与原文的字错率 | **0.0269** | 0.1060 | ≤ 0.02 | **0%** |
| 整轮延迟（13.8 秒口述） | **P50 198 ms / P95 204 ms** | — | — | — |
| 建议在飞上限 | **8 路** | — | — | 吞吐 97% 峰值，P95 860 ms |

最后一列要解释一下：把 986 条反复重抽 4000 次，每次重算一遍指标，数它有
多少次仍落在线内侧。这比只看一个点诚实：贴着线的指标，换一批句子就可能翻到
线外。按这个读法：清除和空输出是稳的；内容保留和编造只有六成和五成的重抽落在
线内，正确的说法是「和线分不清」，不是「过了」；字错率明确没过。

字错率没过的构成：0.0269 里有 0.0127 是识别器听错的字，润色器被锁成只能删，
改不了；另有 0.0041 是把语料自己带的口语词也删了，对听写产品来说那是对的。
两项相加 0.0168，就是这套架构在这把尺子上的地板。地板本身在线以下，
所以判据不是不可达，可达的还剩约 0.010。

留出集的口语词是我们自己插进去的，所以另外拿 230 段真人长口述（RAMC）再量
一遍。这把尺子不用人工标签：该删的只认最没有争议的两类（嗯/呃、紧挨着的整段
重复），少删就掉分；同时数「没有任何理由支持的删除」，多删就涨。两头拉着，
偏袒不了任何方向：

| | 产品（两条臂） | 只有生成式 | 真人编辑 |
| --- | ---: | ---: | ---: |
| 嗯/呃 删掉 | **0.9902** | 0.7781 | 0.9835 |
| 整段重复删掉 | 0.8889 | 0.5881 | 0.9296 |
| 没理由的删除（每千字） | **11.57** | 29.2 | 37.99 |
| 否定词存活 | **0.9982** | — | — |

口语词清除已经过了真人编辑的线，误删只有真人的三成。剩下的缺口在重复那一格：
差 0.041，369 处里约 15 处。

说话期间的预览（四段真听写，每秒刷一次）：第一个字 2.5 秒出现，占卡约
5.7% 的实时率，显示的文本和松手后的最终转写逐字相同。

## 4. 边界

1. **字错率没到自拟的 0.02。** 0.0269，重抽 4000 次里一次都没落到线内。
   可达空间还剩约 0.010，要过线得吃掉其中七成。那要重训一轮，
   合并层面能拧的螺丝已经拧完了。
2. 内容保留和编造贴在线上。0.9803 和 0.0199 看着都过，但重抽里只有 62% 和
   54% 落在内侧，换一批句子重跑可能就掉出去。
3. 识别器听错的字改不了。润色只能删，「客户那边」听成「客户拿边」这类错一个
   都纠不了，占字错率的 47%。换来的是编造被结构性压住，这是一笔知情的交换。
4. **删口语词时会连着吃掉旁边的内容字。** 自己部署上去用，读出来两处：
   「就是我们那个那个会议」出来是「就是我们会议」（该删的删了，留下的话不通）；
   「就是说需要发票」出来是「说需要发票」（孤零零一个「说」）。总量上它比真人
   编辑保守（11.57 对 37.99 每千字），但这两句读者一眼就能看见。
5. **真人自发语音上删得比留出集显示的多。** 60 段真人口述过整条链：转写 5252
   字，删了 354 字（6.74%）。删掉的字里只有 16.4% 在口语词表内、21.8% 是去掉
   一份重复，剩下 61.9% 两样都不是。里面有口语词串，也有真删了内容的：

   ```
   听成 …你咱们学校是不是还有一个宗教信仰那那那社团了？
   出来 …学校是不是还有一个宗教信仰社团了？        ← 「咱们」跟着「你」一起没了
   听成 我感觉就是这个西方人是我感觉他想象力也特别强
   出来 我感觉这个西方人是我想象力也特别强          ← 「感觉他」被删，句子读不通
   ```

   留出集看不见这一格：那里的口语词是按概率插进去的，真人是把口语词和实词
   绞在一起说的。这是目前最该继续量的一条。
6. 短于 1.5 秒的音频，语言判定不可靠：半秒的「嗯」会被判成日语。现在短音频
   直接用部署声明的语言（`MINDSURF_ASR_LANGUAGE`，默认 `zh`），长音频照旧
   自动判。这不是把模型变准了，是绕开了它不准的那一段。
7. 噪声还是会冒字。45 段合成噪声里 22 段出了字：白噪、粉噪、工频嗡、人声嘈杂
   全写成「嗯。」，键盘敲击写成「The.」。试过按帧能量的变异系数在识别器出口
   挡，量出来不能用：稳态噪声最高 0.364，会议室免提的真人语音最低 0.232，
   两个分布重叠，没有一个阈值能同时安全又有用。
8. 热词够不着两类：声母不同的（「李欣」对「吕鑫」，无声调拼音也不同音），
   和被分词器读成几个正常词的（句首的「通一千问」切成「通/一千/问」）。
   解码期偏置能治第一类，实测不划算：召回 8/9 → 9/9，但陷阱句改坏
   1/10 → 3/10、慢四倍、还丢标点。
9. 长录音的分段参数是在合成语音上调的，停顿分布是合成器的不是人的，90 秒
   那个拐点在真人录音上可能会动，仓库里没有真人长录音可验。松手后的等待仍随
   录音长度增长，分段把它从线性压到了亚线性（900 秒从 4263 降到 1861 ms），
   要变成常数（约 55 ms）需要客户端边录边送。
10. **说话期间的预览只在「一个人对着麦克风口述」这个场景上成立。** 四段真听写
    上显示的文本逐字等于最终转写；同一套测试放到双人对话上，八段零段一致，
    p90 有 50 个字被改写——抢话、重叠、改口会让识别器反复改主意。另外那四段
    录音都只有 13.5 到 13.9 秒，一分四十九秒那次是拼接出来的，不是真的长听写。
11. **判据的天花板是别人的对话标注。** 无标签探测器只认 嗯/呃 和紧挨着的整段
    重复（对着 CS2W 的人工标签验过，按处算 94.9% 和人一致），因为那份语料说
    其余候选词只有两成上下是口语词。真人的改口不是整段复制，探测器找不到。
    听写场景的带标注音频我们一条都没有，所以所有召回都只是「在这个高把握子集
    上的召回」。
12. 160 字那道分组闸本身没量过。闸之下整条送、闸之上按句切，两半各有数据支持，
    但闸该定在哪没有：留出集最长 170 字，长口述从 160 字起，没有一条落在
    线附近。
13. **没有客户端。** 产品定义是「按住说话 → 松开 → 文字进输入框」，后半句一个
    字都没实现，仓库里 grep `clipboard|hotkey|paste` 零命中。对标下来这也是
    同类产品故障率最高的一面（Citrix、RDP、VMware、银行应用、终端各有各的
    坏法）。

## 5. 许可

**当前产出物不可商用。** 文本基座继承训练数据的 CC-BY-NC-4.0，并传导到所有
微调结果。`GET /v1/models` 会在响应里带 `commercial_use_permitted: false`，
让这件事没法被忽略。

朗读走 edge-tts，是托管服务：要念的文本会离开本机。所以它默认关着。

## 6. 怎么复测

逐条读数都在 [`artifacts/`](artifacts)，不用重跑训练。

```bash
uv sync --extra dev

# 听写：986 条留出集走服务真路径
python scripts/measure_polish_service.py \
  --pairs artifacts/polish_train/pairs_holdout.jsonl \
  --checkpoint out/sft_polish6_768.pth --minimind-root ../minimind-o \
  --tagger out/polish_tagger_unionchar.pt \
  --tagger-backbone out/polish_tagger_unionchar_backbone.pth \
  --tagger-threshold 0.4 --device cuda

# 长口述：230 段 RAMC，不需要人工标签的那把判据
python scripts/measure_group_length.py \
  --data artifacts/polish_train/pairs_long.jsonl --split val --lengths 1 \
  --checkpoint out/sft_polish6_768.pth --minimind-root ../minimind-o \
  --tagger out/polish_tagger_unionchar.pt \
  --tagger-backbone out/polish_tagger_unionchar_backbone.pth

# 识别器对标
python scripts/measure_recogniser_bench.py --help

# 四道交付闸
python -m pytest -q
python scripts/verify_delivery.py
python scripts/release_gate.py --range origin/main...HEAD
python scripts/smoke_service.py --base http://localhost:8000   # 需要服务在跑
```

两个容易踩的坑：别用 `uv run pytest`（dev 依赖是 extra 不是 group，`uv run`
不装它）；测试要用装了 torch 的解释器——项目 `.venv` 里没有，用它跑会看到
二十多条「失败」，那是环境不是代码。

## 7. 仓库地图

```text
src/mindsurf_omni/
  service/     推理服务：识别、润色、装配、HTTP 与 WebSocket
  data/        造训练数据用的合成器
  evaluation/  字错率等判据
scripts/       训练、评测、复现用的命令行工具
tests/         契约与仪器的回归
configs/       release/ 下的模型卡与数字来源
artifacts/     每个数字的逐条读数（音频与权重不入库）
docs/          两份正文：接入指南、训练说明
assets/        tokenizer
examples/      一份能跑的客户端
```

`configs/release/` 下那两份 `*_CARD.md` 是 Hugging Face 两个仓的 README。

上游：[预训练仓库](https://github.com/io-wy/MindSurf/tree/pretrain)（基座怎么
来的）、[MiniMind-O](https://github.com/jingyaogong/minimind-o)（模型架构，
Apache-2.0）、[SenseVoice-Small](https://huggingface.co/FunAudioLLM/SenseVoiceSmall)
（识别器）。
